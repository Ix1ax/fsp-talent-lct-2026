# Идентификация пользователей в админке

## Что изменилось

Администратор может узнать пользователя по указанному имени, подтверждённой почте аккаунта,
контактной почте кандидата и неизменному локальному ID. Изменение ФИО не меняет ID и не
позволяет обойти блокировку. Доступны и скрытые, и заблокированные профили.

Используется отдельная административная сессия `/api/v1/admin/auth/login`.
Методы доступны активным `admin` и `superadmin`, ответы — `private, no-store`.
Обычный JWT работодателя/кандидата не предоставляет доступа к этим данным.

## Источники и поля

`GET /api/v1/admin/users`, `GET /api/v1/admin/users/{id}` и ответ
`PATCH /api/v1/admin/users/{id}/status` дополнены одинаковыми полями:

| Поле | Значение |
| --- | --- |
| `full_name` | ФИО из `candidate_contacts`; если его нет — имя проверенной OIDC-идентичности |
| `full_name_source` | `candidate_contacts`, `identity` или `null` |
| `email` | Подтверждённая почта аккаунта из OIDC; отдельно от контактной почты |
| `contact_email` | Самостоятельно введённая контактная почта кандидата, либо `null` |
| `identity_updated_at` | Дата последнего обновления снимка идентичности, либо `null` |

Имя не является подтверждением юридической личности: кандидат и провайдер авторизации
могут разрешать пользователю самостоятельно его менять. ID остаётся главным идентификатором
для блокировки. Не подставляйте выдуманное ФИО вместо `null`: показывайте почту или ID.

Имя OIDC берётся из `name`, иначе из `given_name` + `family_name`. Необязательное некорректное
или слишком длинное имя игнорируется, не ломая вход. Почта должна быть подтверждена и корректна.
Телефон, Telegram, issuer, subject, пароли, токены и приватные файлы в админский ответ не добавлены.

При регистрации имя/почта сохраняются из проверенного JWT, а не из полей тела запроса.
`GET /api/v1/me` обновляет снимок для существующего аккаунта, включая заблокированный; удалённые
аккаунты не обновляются. Повтор того же JWT не меняет дату. Старый JWT не откатывает сведения,
сохранённые из более нового JWT. `/me` по-прежнему не возвращает чужие или новые личные поля.

## Поиск и связанные компании

`GET /api/v1/admin/users?q=Иван&role=candidate&status=blocked&limit=20&offset=0`

`q` ищет подстроку без учёта регистра в ФИО кандидата, имени OIDC, обеих почтах,
ID пользователя и ID кандидатского профиля. `%` и `_` — обычные символы, не шаблоны SQL.
До 200 символов; остальные фильтры работают совместно. Пагинация и total считаются по одному
фильтру в согласованной транзакции; несколько внешних идентичностей не дублируют пользователя.

`GET /api/v1/admin/users/{id}/companies?limit=20&offset=0`

Возвращает `{items,total,limit,offset}`. Элемент содержит `company_id`, `company_name`,
`company_status`, `verification_status`, `role`, `status`, `joined_at`. `role/status` относятся
к членству, `company_status` — к доступу всей компании. Неактивные членства также включаются.
Сортировка `joined_at DESC, company_id DESC`. Пользователь без компаний получает пустой список,
несуществующий ID — 404. Разрешена только пагинация: limit 1..100, offset 0..10000.

`GET /api/v1/admin/companies/{company_id}/members` дополнен полями идентификации из таблицы
выше, а также `user_role`, `user_blocked_reason`, `user_blocked_at`. Существующий `user_status`
показывает статус аккаунта; `role/status` продолжают означать роль и статус членства.

В `/api/v1/admin/audit-events` добавлены `actor_email` и `actor_name`.
Администратор определяется по email и ID, пользователь — по имени/подтверждённой почте и ID.
Системные события не получают чужого автора. Это текущие сведения, а не снимок имени на дату
события: персональные значения не копируются в сохранённые события и их metadata.

## Правила видимости по ТЗ

ТЗ, раздел 2.1 и пункт 2.2(2): контакты кандидата раскрываются работодателю после принятия
приглашения или самостоятельного отклика. Самостоятельных откликов в текущем API нет.
Административный просмотр прямо не описан в ТЗ и добавлен по продуктовому запросу для модерации.

Новые поля выдаются только административными методами. Поиск кандидатов, рекомендации,
карточка банка, события просмотра, обычные участники компании и списки приглашений не получают
ФИО, контактную или аккаунтную почту кандидата. Снимок OIDC в эти DTO не включается.
Кандидат может читать собственные контакты и формировать свой PDF через защищённые `/me`-методы.

Единственное существующее раскрытие работодателю — защищённый
`GET /api/v1/companies/{company_id}/offers/{offer_id}/candidate-contacts`:
принятое приглашение, активная компания, активный owner/recruiter, активный кандидат и действующее
согласие на обработку данных. Возвращаются только контакты из профиля, а не почта OIDC.
До принятия, чужой компании и viewer — 404; после отзыва согласия — 409 `contacts_unavailable`.
Наличие нового административного снимка не обходит эти условия.

## Миграция и заполнение старых аккаунтов

`20261010003124_admin_user_identity_profiles.sql` добавляет nullable-поля в `external_identities`.
Старые записи сохраняются. Предыдущая версия API совместима с расширенной таблицей, но не
заполняет новые поля. Новый API запускается после применения миграции. Down удаляет только
этот снимок; роли, блокировки, связи пользователей и контакты кандидатов не затрагивает.
Новых переменных окружения нет.

Для старых аккаунтов почта/имя OIDC могут быть `null` до следующего `/me`.
Чтобы админка сразу показывала имеющиеся данные, есть одноразовая команда `sync-user-identities`.
Она принимает JSON-массив ответа Keycloak Admin `/users` или объект экспорта realm с `users`.
Используйте точный issuer и время получения актуальной выгрузки:

```sh
# Из apps/api, с существующим DATABASE_URL в окружении.
go run ./cmd/sync-user-identities \
  -issuer http://localhost:8180/realms/fsp \
  -file /absolute/path/users.json \
  -observed-at 2026-10-10T00:30:00Z
```

`-file -` (по умолчанию) читает stdin. Команда также включена в Docker-образ API:

```sh
docker compose --profile app run --rm --no-deps -T \
  --entrypoint sync-user-identities migrate \
  -issuer http://localhost:8180/realms/fsp \
  -observed-at 2026-10-10T00:30:00Z < /absolute/path/users.json
```

Время в примере замените временем вашей выгрузки. Не используйте старый экспорт с текущей
датой. Внешние аккаунты сопоставляются только по `(issuer,id)`, новые пользователи не создаются,
роли/блокировки не меняются. Неподтверждённая почта не сохраняется как подтверждённая.
Вся выгрузка проверяется и применяется одной транзакцией. Более старый снимок не заменяет новый.
Повтор с теми же данными и временем не меняет записи. Пропущены — неизвестные/удалённые
аккаунты, устаревшие снимки или уже совпадающие данные. В выводе только количества.
Экспорт не нужно добавлять в репозиторий; API не получает постоянных прав Keycloak Admin.

## Проверки

Интеграционные тесты проверяют сохранение из JWT, защиту от подмены тела регистрации,
обновление и старые токены, поиск по кириллице/почте/ID, скрытые и заблокированные профили,
несколько идентичностей, членства и пагинацию, административные права, импорт и его атомарность,
авторов журнала и отсутствие персональных данных в обычных ответах работодателя.
Существующие тесты раскрытия контактов проверяют согласие, принятие приглашения, чужие
компании, viewer, блокировки и приватность журнала. Миграции проверяются на изолированных
схемах PostgreSQL, включая сохранение ранее существовавших блокировок.
