# Операционные методы админки

## Объём и связь с ТЗ

До этой доработки админка уже управляла отдельными аккаунтами администраторов, справочниками,
модерацией навыков, банком вопросов, шаблонами тестов и предпросмотрами. Дополнены операционные
сценарии существующих модулей: компании, подтверждение компаний, пользователи, потребности,
ежедневные задания, приглашения, попытки кандидатов, статистика и общий журнал действий.

Добавлено 22 административных маршрута и 2 маршрута подачи/чтения заявки работодателем.
Полный машинный контракт находится в `api/openapi.yaml`, одинаковая встроенная копия — в `/openapi.yaml`.
Фронтенд в этой доработке не изменяется.

В пункте 2.2(4), страница 5 ТЗ, верификация компаний и модерация вакансий вынесены за рамки
обязательного MVP. Подтверждение компании добавлено по продуктовому запросу и не является
обязательным условием использования поиска, приглашений, потребностей или заданий.
Категория и грейд по-прежнему определяются тестированием: административное редактирование
результатов, подтверждённых навыков, категории и ответов кандидатов не добавляется.
Потребность работодателя не приравнивается к опубликованной вакансии; самостоятельного
модуля вакансий/откликов в текущем бэкенде нет, эти сущности не имитируются административным CRUD.

## Авторизация и видимость

Административные методы используют существующую отдельную сессию: `POST /api/v1/admin/auth/login`,
затем `Authorization: Bearer <admin_access_token>`. Токен Keycloak сайта сюда не подходит.
Все новые административные методы доступны активным `admin` и `superadmin`, кроме блокировки
исторической записи `users.role=admin`: она разрешена только `superadmin`. Управление настоящими
аккаунтами `admin_accounts` остаётся в `/admin/admins` и доступно только `superadmin`.

Полномочия повторно проверяются репозиторием в транзакции, включая статус администратора.
Блокировка администратора существующим API отзывает его сессии. Ответы имеют
`Cache-Control: private, no-store`. Запросы и тела с персональными данными не пишутся в HTTP-журнал.

Пользователи показываются через ID, роль, статус, даты, ID профиля и статус поиска. Контакты,
внешние issuer/subject, токены и пароли в эти ответы не включаются. Просмотр приглашений не
раскрывает контакты кандидата и не даёт администратору изменять ответ кандидата. Просмотр попытки
отдаёт только метаданные и общий результат, без ответов, вопросов и снимков правил оценки.
Администратор скачивает документы компании для проверки и файл публичного задания; новые
методы не дают доступа к приватным файлам решений кандидатов.

## Маршруты

Административные пути ниже имеют префикс `/api/v1/admin`.

| Метод и путь | Назначение |
| --- | --- |
| `GET /stats` | Счётчики пользователей, компаний, потребностей, приглашений, заданий, решений, тестов, ожидающих навыков |
| `GET /audit-events` | Объединённый журнал действий |
| `GET /companies` | Все компании, очередь заявок и фильтры |
| `GET /companies/{company_id}` | Карточка компании, версия и результат проверки |
| `GET /companies/{company_id}/members` | Участники компании с локальным статусом пользователя |
| `GET /companies/{company_id}/files` | Документы компании, включая pending/deleting, без deleted |
| `GET /companies/{company_id}/files/{file_id}/download` | Готовый документ именно этой компании |
| `PATCH /companies/{company_id}/verification` | Подтвердить, отклонить или отозвать подтверждение |
| `GET /users` | Пользователи с фильтрами |
| `GET /users/{id}` | Метаданные пользователя |
| `PATCH /users/{id}/status` | Блокировать/разблокировать с причиной |
| `GET /needs` | Потребности всех компаний |
| `GET /needs/{id}` | Потребность с навыками и форматами работы |
| `PATCH /needs/{id}/moderation` | Скрыть потребность или снять модерацию |
| `GET /offers` | Приглашения с фильтрами компании/кандидата/статуса |
| `GET /offers/{id}` | Приглашение для административного просмотра |
| `GET /tasks` | Ежедневные задания, включая скрытые |
| `GET /tasks/{id}` | Задание и число ответов |
| `GET /tasks/{id}/file` | Файл задания |
| `PATCH /tasks/{id}/moderation` | Скрыть задание или снять модерацию |
| `GET /assessments/attempts` | Метаданные попыток кандидатов |
| `GET /assessments/attempts/{id}` | Метаданные и общий результат попытки |

Для работодателя, с обычным employer JWT:

| Метод и полный путь | Доступ |
| --- | --- |
| `GET /api/v1/companies/{company_id}/verification` | Любой активный участник своей компании |
| `POST /api/v1/companies/{company_id}/verification/request` | Только активный владелец своей компании |

Файлы выдаются через API как `attachment`, с `nosniff`, без публичных URL и ключей S3.
Чужой документ в URL другой компании возвращает 404.

## Подтверждение компании

1. Владелец указывает корректный ИНН обычным `PATCH /companies/{company_id}` и загружает хотя бы
   один документ через `/companies/{company_id}/files`, `purpose=company_document`.
2. `POST /companies/{company_id}/verification/request` переводит `unverified`/`rejected` в `pending`.
   Фиксируются ID всех готовых документов, дата и новая версия. Логотип не заменяет документ.
   Без ИНН/готового документа приходит `409 verification_evidence_required`.
3. Администратор получает карточку, список документов, скачивает документ и принимает решение:

```json
{"status":"verified","expected_version":1,"reason":"Проверены реквизиты и документ"}
```

`verified` и `rejected` доступны для `pending`. `unverified` отзывает `verified`. Причина до
2000 символов обязательна для отказа и отзыва; для подтверждения необязательна.
`expected_version` берётся из `verification_version` административной карточки.
Каждый переход увеличивает версию; устаревшее решение получает `409 state_conflict`.
Две противоположные проверки одной версии не перезаписывают друг друга: одна проходит,
вторая получает конфликт и должна заново прочитать карточку. Повтор текущего состояния с
актуальной версией не меняет дату, причину и журнал; повтор со старой версией возвращает 409.

Повтор подачи уже `pending`/`verified` возвращает текущее состояние, не создавая новую заявку.
После отказа или отзыва владелец может подать документы повторно. Работодатель видит статус,
версию, даты, причину и ID документов, без ID проверяющего администратора.

Подтверждение относится к реквизитам и документам конкретной заявки. Изменение названия/ИНН
при `pending`/`verified` или удаление любого документа этой заявки сбрасывает статус в `unverified`,
очищает текущие данные проверки и увеличивает версию. Прежняя история сохраняется в журнале.
Правило защищено триггерами БД; добавление нового документа, описание и контакты не меняют
проверенные название/ИНН. Административная проверка и изменение реквизитов сериализуются по
компании. Старый ответ `PATCH /companies/{company_id}` возвращает уже обновлённый статус.

## Блокировка и модерация

Пользователь: `PATCH /users/{id}/status`, JSON `{status:"blocked"|"active",reason:"..."}`.
Причина обязательна. Статус `deleted` этим API не устанавливается и не восстанавливается.
Блокировка немедленно закрывает доступ через обычную проверку локального пользователя.
Keycloak JWT не отзывается; после разблокировки ещё действующий JWT снова может использовать API.
Существующие профили, согласия, приглашения и результаты не удаляются, роль не меняется.
Повтор того же статуса не создаёт лишних событий.

Потребности и ежедневные задания: `PATCH /{needs|tasks}/{id}/moderation`,
JSON `{status:"hidden"|"published",reason:"..."}`. Причина обязательна.

- Скрытая потребность получает `status=archived`, `moderation_status=hidden`. Работодатель не может
  редактированием обойти запрет. Снятие модерации оставляет `archived`, после чего работодатель
  может актуализировать запись и активировать её через обычную валидацию потребностей.
- Скрытое задание получает `status=closed`, исчезает из списков, карточек и скачивания для
  соискателей; новый ответ запрещён. Компания сохраняет доступ к своему заданию и его ответам,
  кандидат — к истории своего решения. Снятие модерации возвращает видимость, сохраняя `closed`.
  Квота одной публикации компании в день не освобождается.

Статус модерации защищён отдельным полем и не задаётся работодателем. Ограничения БД удерживают
скрытую потребность архивной, скрытое задание закрытым. Изменения и аудит записываются одной
транзакцией, параллельные изменения сериализуются блокировкой записи.

## Списки, статистика и журнал

Списки: `{items,total,limit,offset}`; `limit=1..100` (20 по умолчанию), `offset=0..10000`.
`total` считается по тому же фильтру до пагинации в одной согласованной транзакции.
Неизвестные, повторные, пустые и некорректные параметры возвращают 400.

| Список | Дополнительные фильтры |
| --- | --- |
| Компании | `q` по названию/ИНН, `status=all/unverified/pending/verified/rejected` |
| Пользователи | `role=candidate/employer/admin`, `status=all/active/blocked/deleted` |
| Потребности | `q`, `company_id`, `specialization_id`, `grade_id`, `status=all/draft/active/archived` |
| Приглашения | `company_id`, `candidate_id` (ID профиля), `status=all/sent/viewed/accepted/rejected` |
| Ежедневные задания | `q`, `company_id`, `specialization_id`, `grade_id`, `status=all/published/hidden` — именно модерация |
| Попытки | `candidate_id`, `specialization_id`, `grade_id`, `status=all/active/passed/failed/expired` |
| Журнал | `source`, `actor_id`, `entity_type`, `entity_id`, `action`, `from`, `to` |

Компании: сначала pending, по давности подачи, далее новые компании. Остальные сущности — по дате
создания/публикации/начала DESC, затем ID DESC. Журнал — `created_at DESC, source ASC, id DESC`.
`q` — подстрока без учёта регистра, до 200 символов. Членам и документам доступна только пагинация.

Общий журнал объединяет `operations`, `catalogs`, `assessments`, `admins` и `activity`.
`entity_id` — строковый UUID или числовой ID справочника; `actor_id` — UUID пользователя/администратора.
`from`/`to` — RFC3339 с часовым поясом, включительно. Системный сброс подтверждения имеет
`actor_kind=system`, без присвоения действия конкретному пользователю. В журнале есть ID, действие,
статусы, даты и причина новых операционных решений; сырые metadata старых событий не отдаются.
Пароли, токены, тексты резюме, файлы, ответы и правила тестов не копируются в журнал.

Статистика возвращает согласованные счётчики и `generated_at`. Числа не ограничены пагинацией.
Ролевые счётчики пользователей включают все статусы. Открытые задания учитывают deadline;
статусы попыток отражают сохранённый результат штатного механизма тестирования. `active` с прошедшим
сроком — ожидающая завершения попытка, административное чтение само её не оценивает.

## Миграция и проверка

Миграция `20261009213515_admin_operations.sql` названа по времени создания. Она идёт после
`20261009210234_company_daily_tasks.sql`: добавляет данные проверки компании, модерацию контента,
индексы, журнал и триггеры. Новых переменных окружения нет; используются существующие admin auth,
PostgreSQL и приватный S3. Применение миграций обязательно до запуска нового бэкенда.
Новые поля ответов добавлены в OpenAPI; прежние методы сохраняют контракт с учётом явной модерации.

Откат сохраняет статусы verified/rejected, но удаляет данные заявок, версии, причины и новый журнал.
Pending переводится в unverified. Скрытые задания остаются closed, скрытые потребности — archived;
поле запрета редактирования удаляется. Старые события других журналов, данные и файлы не удаляются.

Проверки выполнялись на временных PostgreSQL 17 и MinIO с `-race`: полный интеграционный прогон
**117 тестов прошёл**, включая 4 новых сценария админки и настоящий S3. Проверены жизненный цикл
заявки, документы чужой компании, версии/конкурирующие решения, сброс при изменении реквизитов и
удалении документа, блокировка JWT-доступа, модерация без обхода, фильтры, статистика, аудит,
отдельная авторизация, Up/Down/Up и прежние сценарии платформы.

```sh
cd apps/api
go test -race ./...
go vet ./...
TEST_DATABASE_URL='postgres://...' TEST_S3_ENDPOINT='http://...' TEST_S3_BUCKET='...' \
TEST_S3_ACCESS_KEY='...' TEST_S3_SECRET_KEY='...' GIN_MODE=release \
  go test -race -tags=integration ./tests/integration -count=1
```
