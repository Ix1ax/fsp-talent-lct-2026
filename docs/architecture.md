# Архитектура

Для хакатона используем модульный монолит: один Go-процесс и одна БД. Это проще развернуть и менять командой, а разделение по предметным областям оставляет возможность выделять сервисы позже.

## Выбор инструментов

Gin работает с `net/http`: обычные контексты, middleware и инструменты Go подключаются без адаптеров. Для этого проекта скорость запросов к БД и внешним сервисам важнее разницы между HTTP-фреймворками. Fiber тоже подходит, но сейчас дополнительных причин выбирать его нет.

PostgreSQL — источник истины. `pgxpool` держит ограниченный пул подключений. Redis используется только как восстанавливаемый кеш: память ограничена, включено вытеснение, сохранение на диск отключено. Не хранить здесь единственную копию сессий, заданий или очереди.

S3 нужен для приватных резюме, документов и экспортов. По умолчанию поднят SeaweedFS 4.37 в режиме `mini`; это один узел с volume, а не отказоустойчивый кластер. AWS SDK v2 и path-style адресация позволяют заменить его другим S3-провайдером. Бакет создаётся хранилищем при запуске. API только проверяет доступ и не требует права создавать бакеты.

MinIO community не выбран для новой основы: официальный репозиторий архивирован 25 апреля 2026 года. Источники: https://github.com/minio/minio, https://github.com/seaweedfs/seaweedfs, https://gin-gonic.com/en/docs/.

## Как раскладываем бекенд

```text
cmd/api                  сборка приложения и жизненный цикл сервера
cmd/migrate              отдельный процесс миграций
internal/config          чтение и проверка окружения
internal/platform        подключения к Postgres, Redis и S3
internal/httpapi         маршруты, middleware, HTTP-ошибки
internal/auth            проверка OIDC-токенов
migrations               SQL, встроенный в бинарник migrate
```

Новые модули добавляем по мере реализации: `candidate`, `employer`, `assessment`, `matching`, `invitation`, `fsp`. В модуле держим сервис с правилами, репозиторий с SQL и HTTP-обработчики. Зависимости передаём через конструкторы; транзакции и правила перехода статусов остаются в сервисах. Интерфейсы вводим там, где нужна подмена или есть несколько реализаций.

## Что следует из ТЗ

Это список дальнейшей реализации, не утверждение о готовности функций:

- Главный сценарий: работодатель ищет кандидатов по подтверждённой категории и отправляет приглашение с диапазоном зарплаты в рублях.
- Самоописание и подтверждённый грейд хранятся отдельно. Категория появляется после тестирования; смена грейда ограничивается по времени.
- Контакты кандидата отделены от публичного профиля. Выдавать их можно только после принятия приглашения или самостоятельного отклика. Проверять принадлежность записи в SQL и сервисе, не только роль в middleware.
- В будущих модулях роль должна браться из локальной БД. Не доверяем роли из тела запроса или произвольному claim провайдера.
- ФСП-интеграция — интерфейс с синтетическим адаптером до появления реального API. Отсутствие истории ФСП — нормальное состояние, а не ошибка.
- Согласия и приватность требуют отдельных полей/событий, истории изменений и проверки перед публикацией данных.
- Генерацию заданий, разбор PDF и экспорт выносим в фоновые задания, когда появятся реальные обработчики. Нельзя исполнять присланный кандидатами код внутри API-контейнера.

## OIDC и файлы

В ТЗ Keycloak указан как ориентир. Здесь готова серверная проверка OIDC JWT, но сам провайдер и экран входа пока не развёрнуты. Для Keycloak настройте audience `fsp-api`, claim `email_verified`, обязательное подтверждение почты и отдельный публичный SPA-клиент с Authorization Code + PKCE. Не передавайте ID token вместо access token; access token должен содержать ожидаемые claims и audience.

Для нового issuer локальная учётка определяется парой `(issuer, subject)`. Связь аккаунта с ФСП ID должна требовать подтверждения владения, а не простого ввода чужого ID.

S3 не опубликован наружу в production. В следующих модулях загружайте файлы через авторизованный API с ограничением размера и проверкой формата. Presigned URL добавляйте только вместе с доступным браузеру S3-доменом, CORS и проверкой владельца: внутренний hostname `s3` из Docker в браузере не работает.

## Монорепа

В корне один npm workspace. Go остаётся самостоятельным модулем в `apps/api`; `go.work` пока не нужен, потому что Go-модуль один. Общий контракт — `api/openapi.yaml`. Добавлять `packages/*` и генерацию клиента имеет смысл, когда появятся общие библиотеки и продуктовые методы.

CI проверяет обе части и их совместный запуск. Docker-контекст API ограничен его директорией; фронтенд собирается из корня, чтобы видеть workspace lock-файл. Образы версионируются SHA коммита и деплоятся вместе.
