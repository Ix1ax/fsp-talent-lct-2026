# Деплой и секреты

## Что делает автоматизация

CI работает на PR и push в `main`: Go format/vet/race-тесты, фронтенд lint/build и сборка всего Compose-стека со smoke-проверками. После успешного CI для push в `main` workflow `Release and deploy` публикует API и web в GHCR с тегом SHA проверенного коммита. PR не получает production-секреты и не запускает деплой.

Деплой включается repository variable `DEPLOY_ENABLED=true`. По умолчанию публикация работает без VPS, шаг деплоя пропускается. Целевой сервер — Linux x86_64 с Docker Engine и Compose v2; контейнеры публикуются для amd64. Локально Docker собирает образы под вашу архитектуру.

## Что добавить в GitHub

Создайте Environment `production` в Settings → Environments. Значения никто не создаёт автоматически: заполните их сами.

| Secret в environment production | Значение |
| --- | --- |
| `DEPLOY_HOST` | IP или DNS сервера, без протокола; SSH на порту 22 |
| `DEPLOY_USER` | Отдельный SSH-пользователь с доступом к Docker |
| `DEPLOY_SSH_KEY` | Приватный ключ этого пользователя |
| `DEPLOY_KNOWN_HOSTS` | Проверенная запись host key сервера для `known_hosts` |
| `PRODUCTION_ENV` | Полное содержимое заполненного `deploy/production.env.example` |

`GITHUB_TOKEN` выдаёт GitHub автоматически; workflow использует его только для публикации пакетов. Для приватных GHCR-пакетов сервер нужно отдельно авторизовать токеном с `read:packages`; храните этот токен в серверном Docker credential store. Не вставляйте его в репозиторий. Если пакеты публичные, авторизация на сервере не нужна.

`PRODUCTION_ENV` содержит пароли Postgres/Redis/S3, S3 key и bucket, DOMAIN, OIDC_ISSUER и OIDC_CLIENT_ID. Генерируйте пароли командой `openssl rand -hex 32`: так значения безопасны для Compose и DSN без дополнительного URL-кодирования. Не используйте пробелы, `$`, `@`, `:` и переводы строки внутри значений. Пароль существующего Postgres-volume не меняется простым изменением env — ротация требует изменения роли в БД.

## Подготовка VPS

1. Установите Docker/Compose и создайте deploy-пользователя. Доступ к Docker фактически даёт права администратора сервера.
2. Добавьте публичную часть SSH-ключа в его `authorized_keys`. Получите host key через доверенный канал и заполните `DEPLOY_KNOWN_HOSTS`.
3. Направьте DNS `DOMAIN` на сервер, откройте TCP 80/443 и при необходимости UDP 443. Базы и S3 наружу не публикуются.
4. Подготовьте OIDC-провайдер с HTTPS, audience API и подтверждением email; настройка Keycloak описана в архитектуре.
5. Если GHCR приватный, выполните на сервере `docker login ghcr.io` от deploy-пользователя с read-only токеном.
6. Добавьте секреты, установите repository variable `DEPLOY_ENABLED=true`, влейте PR в `main`.

Workflow копирует серверный Compose, Caddyfile и `.env` в `~/fsp`, скачивает образы, применяет миграции, запускает сервисы и проверяет readiness. Права на директорию — 700, на `.env` — 600. Caddy получает TLS-сертификат автоматически. После первого запуска проверьте `https://ваш-домен/readyz` снаружи.

## Эксплуатация и откат

На сервере: `cd ~/fsp && docker compose logs -f --tail=100`. Логи не должны содержать тела резюме, токены и персональные данные.

Перед миграциями с изменением существующих данных делайте `pg_dump` и храните копию вне VPS. Резервируйте также volume S3; текущий Compose не обеспечивает автоматические бэкапы или отказоустойчивость. Redis — кеш, его потеря допустима.

Для отката укажите предыдущие SHA в `API_IMAGE`/`WEB_IMAGE` внутри серверного `.env`, затем `docker compose pull && docker compose up -d --wait`. Это откат приложений, а не БД. Схема должна быть совместима; автоматического rollback миграций нет. Неудачная новая миграция останавливает workflow до обновления API.

В GitHub желательно включить защиту `main` и разрешить deployment environment только для main. Секреты и инфраструктура ещё не настроены этим бойлерплейтом: удалённого репозитория и адреса VPS в задаче нет.
