## Маршрут проверки

1. Войти работодателем и выбрать **«Демо · Скаут Технологии»**. Посмотреть документы и команду, переключить страницы потребностей и банка кандидатов, открыть потребность и рекомендации, изучить профиль кандидата.
2. Открыть предложения: у основного кандидата есть все пять отображаемых статусов. Для принятого предложения **«Принято · контакты доступны»** доступны контакты владельцу и рекрутеру. Этому офферу уже 45 дней, он остаётся `accepted`, а не `expired`.
3. В заданиях открыть **«Демо · API списка кандидатов — можно отправить решение»**. Скачать условие и одно из десяти решений, посмотреть профиль автора, оценить решение. Основной кандидат ещё не отвечал на это задание.
4. Войти основным кандидатом. Проверить заполненный профиль, экспорт PDF, историю теста и подтверждённые навыки. Junior Go уже подтверждён; для новой попытки выбрать доступный следующий грейд, например Middle Go. Последний успешный тест был 15 дней назад, активной попытки нет.
5. Проверить предложения: первое можно принять или отклонить, второе просмотрено более семи дней назад, пятое истекло. Открыть задания, скачать условие, загрузить собственное решение первого задания; в истории уже есть две оценки.
6. В разделе ФСП виден демонстрационный снимок достижения. Обновление обращается к существующему mock-адаптеру: после него результат зависит от идентичности аккаунта и может стать пустым. Это штатное поведение mock, не настоящий реестр. Привязка основного кандидата согласована с его реальным Keycloak `sub`.
7. Войти новым кандидатом для проверки согласий, создания профиля и опроса с нуля. Импорт PDF проверяется собственным файлом; чужие реальные резюме в демо-данные не включены.
8. Войти рекрутером и наблюдателем, сравнить доступные действия в основной компании.
9. Войти администратором через `/admin`: рассмотреть навыки на модерации, заявку **«Демо · На проверке»**, скачать документ, подтвердить или отклонить заявку, посмотреть заблокированного кандидата и компанию, скрытое задание и потребность, статистику и аудит. Черновик вопроса **«Демо: каким ключевым словом объявляется функция в Go?»** можно редактировать и публиковать. Существующие шаблоны можно пройти в предпросмотре.
10. Войти суперадминистратором и проверить список и управление администраторами.

Одна компания может публиковать только одно задание в день. Чтобы сразу проверить создание нового задания, выбрать **«Демо · Новая компания»** или создать свою компанию: у основной компании на день первоначального наполнения слот уже занят.

Повторный запуск не возвращает набор в исходное состояние: ответы, проверки, блокировки, оценки, изменения профилей и паролей сохраняются. Ожидающее приглашение имеет демонстрационный хеш без публикуемой ссылки принятия; для проверки принятия приглашения нужно создать новое в интерфейсе, который выдаст настоящую ссылку.

## Включение на сервере

Демо-набор создаётся автоматически при первом запуске мигратора и при обновлении существующего сервера. Новых переменных в `PRODUCTION_ENV` и `.env` добавлять не нужно. Внутренние URL, issuer, существующие доступы Keycloak и S3 передаются из `deploy/compose.yaml`.

После слияния изменений GitHub Actions при следующем деплое загрузит новый образ API и применит миграции перед запуском API. Существующие настройки БД, Redis, S3, Keycloak и активации суперадмина остаются действующими.

Для ручного запуска в каталоге серверного деплоя после обновления образов и `.env`:

```bash
docker compose up -d --wait postgres s3 keycloak
docker compose run --rm migrate up
docker compose up -d --wait api web
docker compose logs --tail=100 migrate
```

Не требуется удалять тома, БД или импортировать realm заново. Наполнение происходит один раз по истории миграций, повторный деплой сохраняет данные. Набор предназначен для текущего тестового сервера с опубликованными демо-паролями.

## Локальный запуск

```bash
make up
# Либо отдельно применить миграции и наполнить данные:
make migrate
```

`make up` собирает текущий код и создаёт набор автоматически. `make migrate` поднимает нужные хранилища и собирает мигратор; `make demo-seed` — алиас для той же команды. Адрес фронта в Docker — `http://localhost:3000`. Для активации локального суперадмина при первом запуске задать два `ADMIN_BOOTSTRAP_*` значения в корневом `.env`. Запуск обычных миграций из терминала без Docker требует передать настройки Keycloak и S3; удобнее использовать Compose.

## Устройство миграций и повторный запуск

Три SQL-файла находятся в `apps/api/migrations/demo`, названия используют фактическое время начала создания в Москве (`YYYYMMDDHHMMSS`). История отдельно хранится в `goose_demo_version`; существующая `goose_db_version` и старые миграции не переименованы. Сначала выполняются обычные схемные миграции, затем — однократное наполнение демонстрационного набора.

После SQL мигратор создаёт пять аккаунтов Keycloak с подтверждённой почтой и без обязательной смены пароля, привязывает реальные `sub` к синтетическим пользователям, активирует только новый демо-аккаунт администратора и загружает файлы в S3. Для отметки принадлежности набору в User Profile добавляется единственный атрибут `fsp_demo`, доступный только администратору; остальные настройки сохраняются. Занятый логин вне демо-набора вызывает ошибку, существующий аккаунт не присваивается и его пароль не сбрасывается.

Проверка и загрузка каждого файла выполняются до статуса `ready`. После сбоя можно повторить `migrate up`: применённый SQL не повторяется, загружаются оставшиеся `pending` файлы. Удалённые жюри файлы и готовые объекты не загружаются повторно. Одновременные загрузчики сериализованы блокировкой PostgreSQL.

SQL-откаты предназначены для изолированной проверки набора. Они не удаляют пользователей Keycloak и объекты S3; на сервере с действиями жюри их запускать для «сброса» не нужно. Новые связанные записи могут препятствовать откату — это предпочтительнее их каскадного удаления. Для независимого повтора использовать отдельное окружение.

API-контракты и структура обычных таблиц не меняются. Демо-данные совместимы с текущей версией API; откат самой схемы на старую версию при сохранённых демо-данных требует учитывать внешние ключи, как и любые пользовательские записи.

## Проверки

- `go test -race ./...`: backend-тесты.
- `go test -race -tags=integration ./tests/integration -run TestJury`: применение, откат, повторное применение, количество и состояния данных, сохранение изменений жюри, повтор после сбоя S3, отсутствие сброса пароля и восстановления удалённого файла.
- На настоящих локальных PostgreSQL, Keycloak и S3: вход пяти аккаунтов с `1234`, вход демо-администратора, чтение данных кабинетов, рекомендации и скачивание аватара, условий и решений. Старое принятое предложение остаётся `accepted`, старое ожидающее — `expired`.
