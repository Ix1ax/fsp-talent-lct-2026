# Ежедневные задания компаний

## Связь с ТЗ

На страницах 3–4 ТЗ регулярные короткие задания работодателей описаны как дополнительный свежий
сигнал о кандидате. Этот модуль реализует добровольное участие, файлы заданий и решений и ручную
проверку компанией. Оценка доступна компании и автору решения в отдельной истории. Она не меняет
автоматически грейд, подтверждённую категорию, навыки, ранжирование банка или баллы ФСП.

Квота «одна публикация в день», хранение задания в файле, допустимые форматы и ручная оценка —
продуктовые правила этой доработки; ТЗ не устанавливает эти конкретные ограничения. Заполнение
профиля и прохождение обычных тестов остаются самостоятельными сценариями. Контакты из профиля
не выдаются через API заданий; открытие контактов по приглашению продолжает работать отдельно.
Содержимое загруженного кандидатом файла компания получает целиком: автоматически удалять
контакты из самого файла сервер не пытается.

## Публикации и ответы

- Компания публикует не более одного задания за **календарный день Europe/Moscow** (00:00–24:00).
  Квота общая для всех сотрудников одной компании; у других компаний независимая квота.
  Это календарные сутки, поэтому публикации в 23:59 и 00:01 следующих суток допустимы.
- Владелец и рекрутер публикуют, закрывают приём и проверяют ответы. Viewer только читает
  задания, ответы и скачивает файлы своей компании. Неактивное членство доступа не даёт.
- Администратор может скрыть задание: приём закрывается, карточка и файл исчезают из выдачи соискателей.
  Компания сохраняет доступ к своему заданию; автор — к истории своих решений. Снятие модерации
  возвращает видимость, сохраняя закрытый приём и квоту дня. В карточке есть `moderation_status`.
- Публикация сразу открывает приём. Обязательны `title` (1–200 символов после trim) и файл;
  `description` до 10000 символов, активные `specialization_id`/`grade_id` и `deadline_at` опциональны.
  Отсутствие специализации/грейда означает отсутствие ограничения, а не скрытое значение по умолчанию.
  Эти поля позволяют фильтровать задания; они не запрещают другим кандидатам участвовать.
- Срок приёма задаётся RFC3339 с часовым поясом и должен быть в будущем. По достижении срока
  API считает задание `closed` без фонового задания. Компания также может закрыть приём вручную.
  Повторное закрытие идемпотентно. Закрытие не возвращает квоту дня; редактирования и удаления нет.
- Активные соискатели видят все публикации компаний, включая закрытые. Для чтения и скачивания
  задания профиль и согласия не нужны. Для отправки ответа нужен профиль и действующие глобальные
  согласия `processing` и `publication`; статус поиска `open` не обязателен.
- Один кандидат отправляет **одно окончательное решение** на задание. Замены файла нет;
  повтор возвращает `409 already_submitted`. После закрытия приёма — `409 task_closed`.
- Компания видит ответы только на свои задания от активных авторов с действующими согласиями.
  После отзыва согласия ответ скрывается от компании, включая скачивание файла. Автор сохраняет
  доступ к своей истории. Чужой кандидат не видит ни ответ, ни файл.
- В ответе компании есть `candidate_id` (ID профиля), но нет ID пользователя, контактов профиля,
  bucket, ключа S3 или публичного URL. Отправка решения не создаёт оффер и не продлевает cooldown.
- Проверка принимает `score` (целое 0–100) и/или непустой `feedback` до 5000 символов. Статус
  меняется с `submitted` на `reviewed`, сохраняется дата проверки. Кандидат видит оценку и отзыв.
  Повторная проверка заменяет оба поля; неуказанное поле очищается. Нулевая оценка допустима.

## Файлы и атомарность

Один файл `file`, непустой, до **10 МиБ**. Допустимы PDF, JPEG/PNG (до 4 Мп), ZIP, UTF-8 TXT и MD
без NUL. Проверяется содержимое, а не переданный браузером Content-Type. Для текста нужно расширение
`.txt` или `.md`. ZIP — не больше 1000 записей и 100 МиБ суммарного заявленного размера; сервер
не распаковывает и не исполняет архив. HTML/SVG/исполняемые файлы напрямую не принимаются; исходники
можно приложить архивом. Имена файлов очищаются, ключи хранилища случайные. Неизвестные и повторные
поля multipart запрещены. Тело запроса ограничено 10 МиБ + 64 КиБ; одновременно обрабатывается
до двух загрузок на процесс, остальные получают `503 upload_busy` и `Retry-After: 2`.

Файл сохраняется в существующем приватном S3 bucket. Перед загрузкой проверяются права и квота,
после неё — повторно проверяются права, согласия, срок приёма и уникальность. Готовые метаданные
файла и задание/ответ записываются одной транзакцией. Уникальные ограничения БД защищают квоту
компании и один ответ кандидата даже при гонке. Сбой S3 или откат транзакции не создаёт публикацию
и не расходует квоту; загруженный объект удаляется при очистке. Перед очисткой после ошибки БД
проверяется наличие метаданных, чтобы неоднозначный результат COMMIT не удалил опубликованный файл.
Если S3 или БД недоступны при очистке, ошибка пишется в журнал; объект может остаться без ссылки
до отдельной уборки. Все скачивания идут через API с проверкой прав, `attachment`, `nosniff` и
`Cache-Control: private, no-store`.

## API

Все маршруты имеют префикс `/api/v1` и требуют Bearer JWT соответствующей роли.

| Метод и путь | Действие |
| --- | --- |
| `POST /companies/{company_id}/tasks` | Опубликовать задание, multipart |
| `GET /companies/{company_id}/tasks` | Задания своей компании |
| `GET /companies/{company_id}/tasks/{task_id}` | Карточка задания |
| `GET /companies/{company_id}/tasks/{task_id}/file` | Файл задания |
| `POST /companies/{company_id}/tasks/{task_id}/close` | Закрыть приём |
| `GET /companies/{company_id}/tasks/{task_id}/submissions` | Ответы кандидатов |
| `GET /companies/{company_id}/tasks/{task_id}/submissions/{submission_id}` | Ответ кандидата |
| `GET /companies/{company_id}/tasks/{task_id}/submissions/{submission_id}/file` | Скачать решение |
| `PATCH /companies/{company_id}/tasks/{task_id}/submissions/{submission_id}/review` | JSON с оценкой/отзывом |
| `GET /tasks` | Все задания для соискателя |
| `GET /tasks/{task_id}` | Карточка с `my_submission` |
| `GET /tasks/{task_id}/file` | Скачать задание |
| `POST /tasks/{task_id}/submissions` | Отправить решение, multipart с одним `file` |
| `GET /me/task-submissions` | Мои ответы с оценками |
| `GET /me/task-submissions/{submission_id}` | Мой ответ |
| `GET /me/task-submissions/{submission_id}/file` | Мой файл решения |

Списки возвращают `{items, total, limit, offset}`. `total` учитывает фильтры до пагинации.
Пагинация: `limit=1..100`, по умолчанию 20; `offset=0..10000`.

Фильтры заданий: `company_id`, `specialization_id`, `grade_id`, `q` (подстрока названия/описания,
без учёта регистра, до 200 символов), `status=all|open|closed` (по умолчанию all),
`published_from`/`published_to` (YYYY-MM-DD, обе границы включительно, дата МСК). Соискателю также
доступен `submitted=true|false` — есть ли мой ответ. Задания сортируются по `published_at DESC,
id DESC`: новые выше.

Фильтры ответов: `company_id`, `task_id`, `status=all|submitted|reviewed`, `sort=newest|score`.
Компания дополнительно может задать `candidate_id`. Фильтры только сужают область доступа,
не дают читать чужие записи. `newest` (по умолчанию): `submitted_at DESC, id DESC`;
`score`: `score DESC NULLS LAST, submitted_at DESC, id DESC` — лучшие проверенные решения выше.
Неизвестные, повторные, пустые и некорректные параметры дают `400 validation_error`.

Примеры:

```sh
curl --fail-with-body "$API_URL/api/v1/companies/$COMPANY_ID/tasks" \
  -H "Authorization: Bearer $EMPLOYER_TOKEN" \
  -F 'title=Разработать небольшой API' \
  -F 'description=Требования находятся в приложенном файле' \
  -F 'specialization_id=1' -F 'grade_id=1' \
  -F 'file=@./task.pdf'

curl --fail-with-body "$API_URL/api/v1/tasks?status=open&specialization_id=1&submitted=false" \
  -H "Authorization: Bearer $CANDIDATE_TOKEN"

curl --fail-with-body "$API_URL/api/v1/tasks/$TASK_ID/submissions" \
  -H "Authorization: Bearer $CANDIDATE_TOKEN" -F 'file=@./solution.zip'

curl --fail-with-body -X PATCH \
  "$API_URL/api/v1/companies/$COMPANY_ID/tasks/$TASK_ID/submissions/$SUBMISSION_ID/review" \
  -H "Authorization: Bearer $EMPLOYER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"score":85,"feedback":"Корректная реализация; добавьте обработку ошибок"}'
```

Ключевые ошибки: `409 daily_task_limit`, `409 already_submitted`, `409 task_closed`,
`403 consent_required`, `403 forbidden`, `404 not_found`, `413 file_too_large`,
`415 unsupported_file_type`, `503 storage_unavailable`/`upload_busy`.

## Миграция, настройки и проверка

Миграция `20261009210234_company_daily_tasks.sql` создаёт две новые таблицы
`company_daily_tasks` и `company_task_submissions`. Её имя соответствует времени создания.
Предыдущие таблицы и API сохраняют совместимость; старый API может работать с применённой
миграцией. Миграция должна быть применена до включения нового API; отсутствие новых таблиц
даёт ошибки нового модуля. Откат удаляет задания, ответы и оценки; файлы остаются в существующем
хранилище и таблице `files`. Нужна обычная резервная копия перед откатом с данными.
Новых переменных окружения и bucket не требуется: используется существующая конфигурация S3.

```sh
cd apps/api
go test -race ./internal/dailytask/... ./internal/files/... ./internal/company/service/... ./internal/httpapi/... ./cmd/api/...
go vet ./internal/dailytask/... ./internal/files/... ./internal/company/service/... ./internal/httpapi/... ./cmd/api/...
TEST_DATABASE_URL='postgres://...' GIN_MODE=release \
  go test -race -tags=integration ./tests/integration -run '^TestDailyTasks' -count=1
```

Интеграционные тесты работают на PostgreSQL в отдельной схеме и с файловым хранилищем в памяти:
проверяют Up/Down/Up, права и изоляцию, календарную дату МСК, конкурирующие публикации/ответы,
фильтры, оценку, дедлайн, отзыв согласий/прав во время загрузки, сбой S3 и очистку объектов.
Загрузку в настоящий S3 покрывает существующий тест `TestCompaniesAndPrivateS3` с `TEST_S3_*`.
