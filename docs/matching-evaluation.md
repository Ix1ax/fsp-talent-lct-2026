# Проверка поиска и сходства кандидатов

Проверка на 7 октября 2026 года: 11 синтетических кандидатов, 6 сценариев. Исходные данные и ожидаемые позиции заданы вручную в `apps/api/tests/integration/testdata/candidate_matching.json`, отдельно от алгоритма. Тест использует HTTP API и PostgreSQL; проверяет порядок, оценки, пагинацию и права доступа.

## Правила выдачи

Потребность задаёт предпочтения для рейтинга. Она сама по себе не скрывает другую категорию, превышение бюджета, несовпадающий формат или отсутствие обязательного навыка. Такие расхождения снижают оценку и объясняются. Исключают только явно переданные query-фильтры и правила приватности: активный пользователь, публичный статус профиля, действующие согласия processing и publication.

Неподтверждённые профили доступны по умолчанию. Это продуктовый выбор команды: он не превращает заявленный уровень в категорию, присвоенную тестом. Подтверждённая категория хранится в `category`; без неё это поле равно `null`, а `grade_status` — `unconfirmed`. `declared_category` показывает выбор последней попытки теста; до первой попытки оно тоже `null`. Самоописание резюме не создаёт подтверждённую категорию.

Фильтр `grade_status=all|confirmed|unconfirmed` работает в банке и подборке. Фильтры `specialization_id` и `grade_id` сравнивают подтверждённую категорию, а при её отсутствии — выбор последней попытки. Неизвестные значения не считаются совпадением. Чтобы получить только подтверждённый Junior, отправляют `grade_id=<ID Junior>&grade_status=confirmed`.

### Общее сходство

| Критерий потребности | Вес |
|---|---:|
| Специализация | 30 |
| Грейд | 20 |
| Стек | 30 |
| Формат работы | 10 |
| Бюджет | 5 |
| Город | 3 |
| Часовой пояс | 2 |

`match_score = 100 × Σ(вес × доля совпадения) / Σ(активные веса)`, с округлением до двух знаков. Неуказанное условие потребности исключается из расчёта. Неизвестное значение кандидата даёт ноль по активному критерию. Для числового грейда проверяется точное совпадение, а не автоматическое признание любого более высокого уровня подходящим.

Для стека коэффициент подтверждения тестом равен 1, самооценки — 0,5, отсутствия — 0. Вес обязательного навыка удваивается (`effective_weight = weight × 2`), поэтому его отсутствие сильнее снижает оценку. Покрытие стека возвращается отдельно в `skill_match_score`; без требований к стеку это `null`.

Порядок: подтверждение категории → общее сходство → результат теста категории → UUID. Подтверждённые кандидаты всегда выше неподтверждённых среди профилей, прошедших явные фильтры. Внутри каждой группы выше те, кто лучше соответствует потребности. В обычном банке без потребности сначала идут подтверждённые категории, затем результаты их теста и UUID; общей оценки сходства там нет.

`criteria` раскрывает веса и вклад каждого условия; `mismatched_conditions` — известные расхождения; `unknown_conditions` — недостаток данных; `missing_required_skills` — недостающие обязательные навыки. Контакты и снимки заданий не публикуются. Это оценка соответствия требованиям, а не вероятность успешного найма.

Все шесть сценариев совпали с заранее заданными полными списками и оценками. Проверена каждая из 41 позиции через `limit=1`: порядок и `total` сохраняются. Посторонняя компания получает 404 во всех сценариях. Ответ не кэшируется (`private, no-store`). ivan не появляется даже в расширенном поиске без подтверждения, поскольку приватность остаётся обязательной.

В `candidate_matching_integration_test.go` отдельно проверяются: неподтверждённый профиль с активной попыткой, преимущество подтверждения при одинаковом сходстве, сохранение приоритета подтверждённого профиля даже при меньшем сходстве, явные фильтры зарплаты и навыка, карточка без категории, отзыв согласия и отсутствие утечки контактов. Несовпадения больше не трактуются как скрытые обязательные фильтры.

## Фронтенд

Выбор потребности заполняет предпочтения и включает рейтинговую подборку. Эти значения не нужно автоматически повторять в query-параметрах: иначе они станут жёсткими ограничениями и близкие варианты исчезнут. Для исключения есть отдельное действие «Только совпадающие» либо явно выбранные фильтры.

При переходе в свободный поиск сохраняются поля и предыдущая подборка. Запрос идёт в `/companies/{company_id}/candidates`; при возвращении к потребности — в `/companies/{company_id}/needs/{need_id}/candidates`. Хранение состояния экрана и предыдущих результатов реализует фронтенд; этот этап изменяет API, а не интерфейс.

## Повторный запуск

Нужен отдельный PostgreSQL:

```bash
TEST_DATABASE_URL='postgres://user:password@localhost:5432/fsp_test?sslmode=disable' make matching-evaluation
```

Тест создаёт временную схему, применяет миграции, загружает набор и удаляет схему после завершения. `TEST_DATABASE_URL` обязателен; `-count=1` исключает кэш тестов, `-race` проверяет выполнение с детектором гонок. На рабочий сервер демонстрационные данные не загружаются.

## Границы оценки

Веса и коэффициент самооценки пока не калиброваны на реальных наймах. Проценты разных шаблонов теста не нормализованы по сложности; они используются после сходства и статуса подтверждения. Результат подтверждает соответствие правилам на этом наборе, а не качество найма на реальных данных.

Достижения ФСП пока не участвуют в ранжировании и остаются в `unassessed_criteria`. Их влияние и привязку ФСП ID нужно проверить отдельно после реализации.
