# История компании с кандидатом и повторная выдача

## Связь с ТЗ

Разделы 2.1 и 2.2 ТЗ, страница 5 PDF, требуют ранжирования результатов по соответствию потребности,
учёта силы подтверждённого профиля и достижений ФСП внутри категории, объяснения выдачи и уточнения
запроса без потери подборки. Просмотр работодателем не раскрывает контакты и не изменяет категорию
кандидата. Статус входящего приглашения по-прежнему меняет сам кандидат.

30-дневный срок является дополнительным продуктовым правилом, согласованным в запросе на доработку;
ТЗ не устанавливает такой срок. Полная база доступна через `interaction_status=all`, а прямая карточка
и история офферов доступны в течение срока. Это сохраняет возможность вернуться к полученной подборке.

Давность взаимодействия учитывается после соответствия потребности и силы подтверждённого профиля.
Она не должна ставить более слабого кандидата выше более сильного в той же категории при прочих
равных условиях. Достижения ФСП влияют только внутри подтверждённой категории; отсутствие достижений
не скрывает кандидата.

## Хранение и срок

`company_candidate_interactions` содержит одну запись на пару `(company_id, candidate_id)`:

- `last_viewed_at`: последнее явное открытие профиля или отправка оффера;
- `last_offered_at`: последняя отправка оффера, nullable для просмотра без оффера.

Все сотрудники одной компании используют общую историю. Другая компания имеет независимую запись.
История относится ко всем потребностям компании. Повторные действия не создают дубликаты кандидатов.
Даты обновляются через `GREATEST`, поэтому конкурирующие запросы не уменьшают срок.

`next_available_at = greatest(last_viewed_at, last_offered_at) + interval '720 hours'`.
Ровно в этот момент кандидат снова доступен в обычном поиске. Задание по расписанию не требуется:
фильтрация выполняется при чтении. Просмотр и оффер сохраняются в истории после истечения срока.
Принятие, отказ и просмотр входящего оффера кандидатом не продлевают этот срок.

Успешная отправка сохраняет оффер и историю в одной транзакции. Если отправка завершилась ошибкой,
история не обновляется. Миграция переносит последнюю дату ранее отправленных офферов независимо
от их статуса; старые офферы не получают новый срок от даты развёртывания.

`candidate_profiles.created_at` используется как стабильная дата для равных профилей. Для существующих
профилей миграция использует дату регистрации пользователя, поскольку дата первоначального создания
профиля раньше не сохранялась. Правка резюме не поднимает профиль заново.

## API для фронта

После явного открытия и успешной загрузки карточки вызвать без тела:

```http
POST /api/v1/companies/{company_id}/candidates/{candidate_id}/view
```

Ответ `200` и карточки содержат `has_offer`, `viewed`, `last_viewed_at`, `last_offered_at`,
`next_available_at`. Даты до первого взаимодействия равны `null`. Доступ имеют активные участники
компании `owner`, `recruiter`, `viewer`. GET карточки не меняет историю; POST нельзя вызывать при
предзагрузке, hover или фоновом обновлении. После POST обновить или инвалидировать списки компании,
сохранив выбранные фильтры и потребность.

В этом репозитории экран банка кандидатов пока отсутствует; вызов POST необходимо добавить в обработчик
фактического открытия карточки при подключении этого экрана. Отправка оффера уже обновляет историю
автоматически на беке.

Оба списка кандидатов принимают одинаковые фильтры:

| Фильтр | Значение |
| --- | --- |
| `interaction_status=available` | По умолчанию: нет взаимодействий либо прошло не менее 30 дней |
| `interaction_status=cooldown` | Только кандидаты с неистёкшим сроком |
| `interaction_status=all` | Все доступные профили, включая историю |
| `viewed=true/false` | Было ли взаимодействие этой компании когда-либо |
| `has_offer=true/false` | Отправляла ли эта компания оффер когда-либо |

Например, `interaction_status=all&viewed=true&has_offer=false` возвращает просмотренных без оффера.
Для всех получателей офферов, включая недавно приглашённых, использовать
`interaction_status=all&has_offer=true`. Неподтверждённая категория обозначается отдельно;
фильтр `grade_status=confirmed` позволяет получить только профили с категорией успешного теста.

Фильтры, `total`, сортировка и пагинация применяются в одном снимке БД. Скрытые профили, отозванные
согласия, блокировки и права компании проверяются во всех режимах, включая историю.

## Проверка

```sh
cd apps/api
go test -race ./internal/candidatebank/... ./internal/offer/... ./internal/httpapi/...
# TEST_DATABASE_URL должен указывать на тестовый PostgreSQL.
go test -race -tags=integration ./tests/integration -run '^Test(Candidate(Bank|Interaction|Recommendations|Matching|Details)|Offer|FSP)'
```

Интеграционные сценарии проверяют независимость компаний, историю просмотра без оффера, фильтры,
границу срока и возвращение кандидата, сохранение офферов после отказа, повторные просмотры,
сортировку равных профилей по давности, приоритет соответствия над давностью, приватность,
пагинацию и перенос старых офферов миграцией.

Проверка 9 октября 2026 года: модульные тесты с `-race`, `go vet`, 18 интеграционных сценариев
(включая вложенные проверки) на изолированном PostgreSQL 17, синхронизация OpenAPI и проверка
разрешения ссылок в спецификации прошли. Дополнительный сценарий приоритета результата теста
и достижения ФСП перед давностью просмотра проверен отдельно.
