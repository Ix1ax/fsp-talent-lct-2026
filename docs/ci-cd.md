# Проверки и деплой

При создании или обновлении PR запускается CI: проверки Go, фронта и общего
окружения с Postgres, Redis, S3 и Keycloak. После слияния запускается ещё один
CI для итогового коммита в `main`. Это две проверки разных состояний кода,
а не два деплоя. Не вливайте PR до завершения его проверок.

`Release and deploy` запускается после завершения CI ветки `main`. Публикация
образа разрешена только после успешного CI, вызванного push. При неуспешном
CI задания релиза пропускаются: короткая запись workflow в списке Actions
не означает, что приложение было задеплоено.

Деплой выполняется при `DEPLOY_ENABLED=true` с секретами environment `production`.
Повторный запуск успешного CI для `main` также может запустить релиз повторно.
Деплои выполняются последовательно.

## Время выполнения

На чистом runner скачиваются образы инфраструктуры и запускается Keycloak.
`--wait-timeout 360` — верхняя граница ожидания готовности контейнеров, а не
фиксированная пауза: когда сервисы готовы, Compose продолжает работу сразу.
Время зависит от доступности реестров, кеша и ресурсов runner.

Сборка API и фронта в CI использует Docker Buildx с кешем GitHub Actions.
Compose получает готовые образы через `compose.ci.yaml` и запускается с
`--no-build`. Релиз использует кеш API и публикует только образ бека;
сборка и публикация фронта для серверного деплоя не выполняется.

Первое выполнение после изменения workflow заполняет кеш. Кеш ускоряет повторные
сборки, но не отменяет скачивание инфраструктуры и запуск Keycloak на новом runner.
Кеш PR может быть недоступен последующему запуску в `main`; ветка `main`
заполняет собственный доступный кеш.

Источник: [кеш Docker в GitHub Actions](https://docs.docker.com/build/ci/github-actions/cache/).
