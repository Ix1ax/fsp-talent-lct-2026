# Бэкенд: подбор кандидатов, приглашения, задания компаний и админка

Актуальное описание реализации на 9 октября 2026 года. Документ объединяет сценарии от
потребностей работодателя и банка кандидатов до ежедневных заданий и операционной админки.
Изменения относятся к бэкенду; подключение методов к интерфейсу — отдельная работа.

## 1. Объём реализации и связь с ТЗ

В текущей модели компания создаёт **потребность** (`employer_needs`), под которую получает
подборку кандидатов. Отдельного публичного банка вакансий и модуля откликов на вакансии нет.
Потребности, предложения кандидату и приглашения сотрудников в команду — разные сущности.

ТЗ «ФСП спец. трек» задаёт поиск по соответствию потребности, подтверждение категории через
тестирование, объяснение выдачи, учёт достижений ФСП внутри категории и защиту контактов.
Регулярные задания работодателей описаны как дополнительный свежий сигнал о кандидате.
Подтверждение компаний и модерация вакансий в п. 2.2(4), стр. 5, вынесены за обязательный MVP.

Дополнительно по продуктовому запросу реализованы:

- история просмотров и отправленных предложений отдельно для каждой компании;
- исключение просмотренного кандидата из обычного поиска ровно на 30 дней;
- учёт давности взаимодействия при равной силе профилей;
- одна публикация файлового задания компании за календарный день по Москве;
- одно файловое решение кандидата, ручная оценка и отзыв компании;
- необязательное подтверждение компаний, блокировка пользователей и модерация контента;
- административные списки, статистика и единый журнал действий.

Эти конкретные сроки, квоты и форматы не являются требованиями самого ТЗ.
Оценка ежедневного задания не меняет автоматически категорию, грейд, навыки, бонус ФСП или
ранжирование банка. Подтверждение компании не блокирует использование поиска и приглашений.

## 2. Данные, файлы и общие правила API

**PostgreSQL** хранит записи компаний, потребностей, профилей, предложений, взаимодействий,
заданий, решений, оценок, проверок и аудита. Таблица `files` хранит метаданные файлов.
Сами файлы находятся в приватном S3-совместимом хранилище **SeaweedFS 4.37**, которое задано
в локальном и серверном Compose. Адрес для API внутри Docker — `http://s3:8333`.

Применяются существующие `DATABASE_URL`, `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY`,
`S3_SECRET_KEY`, `S3_BUCKET`. Новые переменные окружения и отдельный bucket не нужны.
MinIO использовался только как временное S3-хранилище для интеграционных проверок;
он не заменяет PostgreSQL и не добавлен в рабочую конфигурацию.

Все пути ниже начинаются с `/api/v1`, если не указан другой префикс.
Обычные методы используют Bearer JWT Keycloak и активного локального пользователя нужной роли.
Административные методы используют отдельный токен сессии админки.

Постраничные списки описанных сценариев возвращают:

```json
{"items":[],"total":0,"limit":20,"offset":0}
```

`total` учитывает фильтры до пагинации. `limit` — 1–100, по умолчанию 20;
`offset` — 0–10000, по умолчанию 0. В новых списках неизвестные, повторные, пустые и
некорректные query-параметры запрещены. Полные DTO, ограничения и ответы — в `api/openapi.yaml`;
встроенная копия находится в `apps/api/internal/httpapi/docs/openapi.yaml` и должна совпадать.
Swagger доступен на `/docs/`, встроенная спецификация — на `/openapi.yaml`.

Ошибки имеют формат:

```json
{"error":{"code":"validation_error","message":"Описание ошибки на русском"}}
```

Базовые статусы: 400 — валидация; 401 — авторизация; 403 — запрет действия;
404 — отсутствующий или недоступный объект; 409 — конфликт состояния;
413 — слишком большой файл/запрос; 415 — неподдерживаемый файл;
500/503 — внутренняя ошибка или недоступный сервис.

## 3. Потребности работодателя

Потребность принадлежит одной компании. Содержит специализацию, необязательный грейд,
название и описание, зарплатную вилку в рублях за месяц, город, часовой пояс, навыки и
форматы работы. Связи хранятся в `need_skills` и `need_work_formats`.
Статусы: `draft`, `active`, `archived`; начальный статус — `draft`.
Для активации нужны хотя бы один навык и один формат работы, остальные поля проходят
обычную валидацию потребности. DELETE архивирует запись.

| Метод и путь | Действие | Доступ в компании |
| --- | --- | --- |
| `POST /companies/{company_id}/needs` | Создать | owner, recruiter |
| `GET /companies/{company_id}/needs` | Список, фильтр status | owner, recruiter, viewer |
| `GET /companies/{company_id}/needs/{need_id}` | Карточка | owner, recruiter, viewer |
| `PATCH /companies/{company_id}/needs/{need_id}` | Изменить | owner, recruiter |
| `DELETE /companies/{company_id}/needs/{need_id}` | Архивировать | owner, recruiter |

`company_id` и автор не меняются через PATCH. Навыки и форматы сохраняются транзакционно.
Справочники общие с кандидатами: `GET /catalogs`, `GET /catalogs/skills`.
Скрытая администратором потребность архивируется и защищена от редактирования работодателем.
После снятия модерации её может актуализировать и активировать работодатель.

## 4. Банк кандидатов и подборка под потребность

Доступ имеют активные участники компании owner, recruiter и viewer с ролью employer.
Отозванное членство не даёт доступа. Чужие компании и профили не раскрываются.
В выдаче только активные кандидаты со статусом поиска `open` или `passive` и действующими
глобальными согласиями `processing` и `publication`. Это действует и для расширенной истории.

| Метод и путь | Назначение |
| --- | --- |
| `GET /companies/{company_id}/candidates` | Свободный поиск |
| `GET /companies/{company_id}/needs/{need_id}/candidates` | Подборка по активной потребности |
| `GET /companies/{company_id}/candidates/{candidate_id}` | Безопасная подробная карточка |
| `POST /companies/{company_id}/candidates/{candidate_id}/view` | Записать фактическое открытие профиля |

`candidate_id` — UUID профиля `candidate_profiles.id`, а не `users.id` или subject Keycloak.
Карточка показывает профессиональные данные, подтверждённую и заявленную категорию раздельно,
результат тестирования, навыки, безопасные сведения об опыте/образовании и достижениях ФСП.
Контакты, идентификатор пользователя и свободные тексты с возможными контактами не выдаются.
GET не записывает просмотр и не меняет категорию.

Оба списка принимают одинаковые фильтры:

| Параметр | Значение |
| --- | --- |
| `specialization_id`, `grade_id` | ID специализации и грейда |
| `grade_status` | all (по умолчанию), confirmed, unconfirmed |
| `skill_id` | UUID навыка |
| `verified_skill_only` | true/false, только вместе с skill_id |
| `work_format_ids` | До 10 уникальных ID через запятую; любой выбранный формат |
| `experience_min_months`, `experience_max_months` | Включительные границы 0–600 |
| `salary_max_rub` | Верхняя граница ожиданий, 0–1000000000 |
| `has_fsp_achievements` | true/false |
| `has_offer` | Отправляла ли именно эта компания предложение когда-либо |
| `viewed` | Взаимодействовала ли именно эта компания с кандидатом когда-либо |
| `interaction_status` | available (по умолчанию), cooldown, all |
| `limit`, `offset` | Пагинация |

Разные фильтры объединяются через И. Неизвестные зарплатные ожидания не проходят явный фильтр
зарплаты. Неподтверждённые профили доступны по умолчанию: заявленный уровень не становится
подтверждённой категорией. Подтверждённая категория возвращается в `category`, заявленная —
в `declared_category`; без подтверждения `category=null`, `grade_status=unconfirmed`.

### Расчёт соответствия

Параметры потребности влияют на рейтинг. Несовпадение грейда, бюджета, формата или отсутствие
навыка снижает оценку, но само по себе не исключает профиль. Жёсткое исключение выполняют
явные query-фильтры, правила приватности и срок после взаимодействия.
Черновая, архивная или чужая потребность не даёт подборку и возвращает 404.

| Критерий | Вес |
| --- | ---: |
| Специализация | 30 |
| Грейд | 20 |
| Стек | 30 |
| Формат работы | 10 |
| Бюджет | 5 |
| Город | 3 |
| Часовой пояс | 2 |

`match_score = 100 × сумма(вес × доля совпадения) / сумма активных весов`,
с округлением до двух знаков. Неуказанный критерий потребности исключается из расчёта;
неизвестное значение кандидата даёт ноль по активному критерию. Грейд сравнивается точно.
В стеке подтверждённый навык имеет коэффициент 1, самооценка — 0,5, отсутствие — 0;
вес обязательного навыка удваивается. `skill_match_score` показывает покрытие стека отдельно.

Подборка возвращает `matching_mode=similarity`, `match_score`, `criteria`, `skills`, `reasons`,
`mismatched_conditions`, `missing_required_skills`, `unknown_conditions`, `unassessed_criteria`.
Это объяснимая оценка соответствия, а не вероятность найма.

### Сортировка и давность

В подборке основной порядок — `match_score DESC`, затем подтверждение категории и результат
теста. Бонус ФСП меняет порядок только при равном сходстве внутри одной подтверждённой
категории; позиции других категорий сохраняются. Бонус по лучшему достижению: место 1–3 — 5,
другое место — 3, участие без места — 1; без подтверждения категории — 0.
`match_score` и грейд от этого бонуса не меняются.

В свободном банке общей оценки сходства нет: сначала подтверждённые категории,
затем результаты теста, с тем же ограничением бонуса ФСП внутри категории.

При равной силе профиля выше кандидат без взаимодействий с компанией, затем тот,
с кем взаимодействовали раньше. Следующие условия — дата создания профиля ASC и UUID ASC.
Правка резюме не обновляет дату создания. Для старых профилей эта дата восстановлена
из даты регистрации пользователя. Пагинация применяется после окончательной сортировки.

## 5. Просмотр, has_offer и возвращение через 30 дней

В `company_candidate_interactions` одна запись на `(company_id, candidate_id)`:
`last_viewed_at` и необязательный `last_offered_at`. История общая для сотрудников
и всех потребностей одной компании. У другой компании независимая история.

`has_offer=true` означает, что **эта компания** когда-либо отправляла кандидату предложение,
включая принятое и отклонённое. Признак сохраняется после окончания срока и учитывает старые
офферы. `viewed=true` означает просмотр или успешную отправку предложения.

```text
next_available_at = max(last_viewed_at, last_offered_at) + 720 часов
```

Это ровно 30 суток, а не календарный месяц. В момент достижения этой даты кандидат
возвращается в обычную выдачу. Cron не нужен: доступность вычисляется при запросе.

| Действие | Результат для этой компании |
| --- | --- |
| Только GET карточки / предзагрузка | История не меняется |
| POST view после фактического открытия | viewed=true; срок отсчитывается от просмотра |
| Успешная отправка предложения | viewed=true, has_offer=true; срок отсчитывается от отправки |
| Ошибка отправки предложения | История не обновляется |
| Повторный просмотр или новый оффер | Срок продлевается |
| Кандидат просмотрел, принял или отклонил оффер | Срок не продлевается |
| Прошло 720 часов | Профиль возвращается; viewed и has_offer сохраняются |

Отправка и обновление истории выполняются одной транзакцией. Конкурирующие запросы
не уменьшают даты. Старые офферы перенесены в историю по времени отправки,
а не по времени применения миграции.

Обычная выдача скрывает кандидата на срок после взаимодействия. Для явного доступа к истории:

```text
?interaction_status=all
?interaction_status=all&viewed=true&has_offer=false
?interaction_status=all&has_offer=true
?interaction_status=cooldown
```

Прямая карточка и история офферов остаются доступны с обычными проверками прав и согласий.
При подключении интерфейса фактическое открытие должно вызывать POST view без тела;
фоновые запросы и hover не должны его вызывать. После просмотра/отправки нужно обновить списки
компании, сохранив выбранные фильтры и потребность. Фронтенд в этой работе не изменён.

## 6. Предложения и доступ к контактам

Оффер принадлежит компании и кандидату. Не создаёт членство кандидата в компании.
Обязательны `candidate_id`, `title`, `description`, обе границы зарплаты и `contact_email`
работодателя. `contact_url` и `need_id` активной потребности этой компании необязательны.
Условия и название компании сохраняются снимком на момент отправки.

| Метод и путь | Действие |
| --- | --- |
| `POST /companies/{company_id}/offers` | Отправить, owner/recruiter |
| `GET /companies/{company_id}/offers` | Список компании, включая viewer |
| `GET /companies/{company_id}/offers/{offer_id}` | Карточка компании |
| `GET /me/offers` | Входящие кандидата |
| `GET /me/offers/{offer_id}` | Карточка кандидата |
| `POST /me/offers/{offer_id}/view` | Отметить просмотр входящего оффера |
| `POST /me/offers/{offer_id}/respond` | accepted или rejected |
| `GET /companies/{company_id}/offers/{offer_id}/candidate-contacts` | Контакты по принятому офферу |

Статусы: `sent → viewed → accepted/rejected`; допустим прямой ответ из sent.
Просмотр идемпотентен. Повтор того же ответа успешен, противоположный ответ после решения — 409.
Конкурирующие противоположные ответы сохраняют одно решение. Повтор POST отправки может
создать ещё один оффер: автоматического ключа идемпотентности этого метода нет.

Списки принимают status, limit, offset; новые офферы идут первыми.
`contact_email`/`contact_url` в оффере относятся к работодателю.
Контакты кандидата получаются отдельным методом: только активному owner/recruiter отправившей
компании, после accepted и при действующем processing. Viewer и чужая компания их не получают.
Выдача контактов журналируется без самих контактных значений. Отзыв processing закрывает доступ.
Чат, отправка письма кандидату, редактирование и отзыв оффера этим модулем не реализованы.

## 7. Ежедневные задания компаний

Каждая компания публикует не больше одного задания за календарный день `Europe/Moscow`.
Квота общая для сотрудников компании; у другой компании своя квота.
Публикации в 23:59 и в 00:01 следующих суток допустимы. Закрытие или скрытие квоту не возвращает.

Публиковать, закрывать приём и оценивать решения могут owner/recruiter;
viewer читает задания и решения своей компании. Активный кандидат видит задания всех компаний,
включая закрытые, кроме скрытых модерацией. Профиль/согласия для чтения задания не нужны.

Публикация — multipart с одним `file`, обязательным title (1–200 символов),
необязательными description (до 10000), specialization_id, grade_id и deadline_at.
Справочники должны быть активны. Специализация и грейд — фильтры поиска задания,
а не запрет участия других кандидатов. Deadline — будущая дата RFC3339 с часовым поясом.

В срок API считает задание closed без cron; также компания закрывает его вручную.
Повторное закрытие успешно. Редактирование и удаление задания не добавлены.

### Ответы и оценка

Для отправки нужен профиль кандидата и действующие глобальные processing/publication;
статус поиска open не обязателен. На одно задание кандидат отправляет одно окончательное
решение. Замены файла нет. Повтор — `409 already_submitted`, закрытый приём — `409 task_closed`.

Компания видит ответы только на свои задания от активных авторов с действующими согласиями.
После отзыва согласия решение и его файл скрываются от компании. Автор сохраняет свою историю;
чужой кандидат её не читает. Контакты профиля через ответы не выдаются, но сервер
не удаляет контакты, которые сам автор включил в содержимое загруженного файла.

Проверка принимает score — целое 0–100 — и/или непустой feedback до 5000 символов.
Ответ становится reviewed, сохраняются дата и автор проверки. Кандидат видит оценку/отзыв.
Повторная проверка заменяет оба поля; неуказанное поле очищается. Оценка 0 допустима.
Отправка решения не создаёт оффер и не меняет срок истории поиска.

### Файлы

Один непустой файл до 10 МиБ: PDF, JPEG/PNG до 4 Мп, ZIP, UTF-8 TXT/MD без NUL.
Для текста обязательно расширение txt/md; тип определяется по содержимому.
ZIP ограничен 1000 записями и 100 МиБ заявленного распакованного размера;
архивы не распаковываются и не исполняются. Прямые HTML/SVG/исполняемые файлы запрещены.
Исходный код можно приложить в архиве.

Multipart не принимает неизвестные/повторные поля, тело ограничено 10 МиБ + 64 КиБ.
Одновременно обрабатываются две загрузки на процесс; при превышении — `503 upload_busy`,
`Retry-After: 2`. Таймаут обработки загрузки — 45 секунд.

До загрузки и перед записью в БД проверяются права, квота, согласия, срок и уникальность.
Метаданные готового файла и задание/решение сохраняются одной транзакцией;
уникальные ограничения защищают дневную квоту и один ответ при гонках.
При ошибке загруженный объект очищается; неоднозначный результат COMMIT проверяется
по метаданным, чтобы не удалить опубликованный файл. Если очистка недоступна,
ошибка журналируется, объект может остаться до отдельной уборки.
Скачивание только через API с проверкой прав: attachment, nosniff, private/no-store,
без выдачи публичного URL, bucket или ключа S3.

## 8. Админка: существующие и новые возможности

Вход: `POST /admin/auth/login` с email/password. Далее
`Authorization: Bearer <admin_access_token>`. Сессия отдельная, срок — 8 часов, refresh нет.
JWT Keycloak сайта её не заменяет. `GET /admin/auth/me` — текущий администратор;
`POST /admin/auth/logout` — завершение сессии.
Начальный superadmin настраивается существующими ADMIN_BOOTSTRAP_EMAIL/ADMIN_BOOTSTRAP_PASSWORD.

Уже существовали управление admin_accounts, справочниками и предложенными навыками,
банк вопросов и версии, шаблоны тестов и серверные пробные прохождения.
Управление аккаунтами через GET/POST `/admin/admins`, PATCH `/admin/admins/{admin_id}`
доступно только superadmin. Блокировка обычного admin отзывает все его сессии;
свой аккаунт и superadmin этим методом заблокировать нельзя. Разблокировка требует нового входа.

Справочники управляются через `/admin/catalogs`, `/admin/catalogs/{kind}`,
`/admin/catalogs/{kind}/{id}`; очередь навыков — `/admin/catalogs/skills/pending`.
Банк тестирования — `/admin/assessments/questions` и `/admin/assessments/templates`:
создание, просмотр, версии вопросов, публикация и архивирование.
Предпросмотры: POST `/admin/assessments/templates/{template_id}/previews`,
GET/DELETE `/admin/assessments/previews/{preview_id}`, PUT ответа в `/answers/{question_id}`,
POST `/submit`. Предпросмотр принадлежит администратору, поддерживает Idempotency-Key
и не создаёт боевые результаты кандидата; лимит — три активных непросроченных прохождения.

Добавлено **22 операционных административных метода** и **2 метода работодателя**.
Все новые административные методы доступны активным admin/superadmin.
Исключение: блокировка исторического users.role=admin требует superadmin.
Полномочия и статус администратора повторно проверяются в транзакции.

задания, но не приватные файлы решений кандидатов. Подтверждённый грейд вручную не меняется.

### Подтверждение компании

Любой активный участник читает `GET /companies/{company_id}/verification`.
Только owner подаёт `POST /companies/{company_id}/verification/request` без тела.
Нужны корректный ИНН и хотя бы один готовый company_document; логотип не заменяет документ.
Без подтверждающих данных — `409 verification_evidence_required`.

Заявка из unverified/rejected становится pending: сохраняются дата, ID всех готовых документов
и новая verification_version. Повтор подачи pending/verified не меняет состояние.
Администратор читает карточку и документы, затем принимает решение:

```json
{"status":"verified","expected_version":1,"reason":"Проверены реквизиты и документ"}
```

Из pending разрешены verified/rejected; verified можно отозвать в unverified.
Причина до 2000 символов обязательна при отказе/отзыве, необязательна при подтверждении.
Каждый переход увеличивает версию. Устаревшая expected_version — `409 state_conflict`;
конкурирующие решения не перезаписывают друг друга. Повтор текущего статуса с актуальной
версией не создаёт событие; повтор со старой версией конфликтует.

Изменение названия/ИНН у pending/verified или удаление документа текущей заявки сбрасывает
статус в unverified, очищает текущую проверку и увеличивает версию. Это защищено триггерами БД;
история остаётся в аудите. Добавление документа, изменение описания/контактов не сбрасывают
проверку. После отказа/отзыва владелец может подать заявку снова.

### Блокировка пользователей и модерация

PATCH `/admin/users/{id}/status`:

```json
{"status":"blocked","reason":"Причина блокировки"}
```

Допустимы active/blocked; причина обязательна. Deleted этим методом не устанавливается
и не восстанавливается. Блокировка сразу закрывает доступ через локальную проверку пользователя;
JWT Keycloak не отзывается, после разблокировки действующий JWT снова пригоден.
Профиль, согласия, предложения и результаты сохраняются. Повтор статуса не дублирует аудит.

PATCH `/admin/needs/{id}/moderation` или `/admin/tasks/{id}/moderation`:

```json
{"status":"hidden","reason":"Причина модерации"}
```

Допустимы hidden/published; причина обязательна. Потребность становится archived,
задание — closed. `moderation_status` отдельное поле, работодатель его не меняет.
Снятие модерации сохраняет archived/closed. Для задания приём не открывается снова,
дневная квота не возвращается. Скрытое задание исчезает из выдачи/карточки/скачивания кандидата;
компания сохраняет собственную запись, автор решения — свою историю.
Изменение и аудит записываются одной транзакцией.

### Фильтры, статистика и аудит

| Административный список | Дополнительные фильтры |
| --- | --- |
| companies | q по названию/ИНН; status=all/unverified/pending/verified/rejected |
| users | role=candidate/employer/admin; status=all/active/blocked/deleted |
| needs | q, company_id, specialization_id, grade_id; status=all/draft/active/archived |
| offers | company_id, candidate_id; status=all/sent/viewed/accepted/rejected |
| tasks | q, company_id, specialization_id, grade_id; status=all/published/hidden — модерация |
| assessments/attempts | candidate_id, specialization_id, grade_id; status=all/active/passed/failed/expired |
| audit-events | source, actor_id, entity_type, entity_id, action, from, to |

Компании pending идут первыми по давности подачи, остальные — новые первыми.
Остальные сущности сортируются по дате DESC и ID DESC. q — подстрока без регистра до 200 символов.
У списков участников/документов только пагинация. candidate_id всегда относится к профилю.

Аудит объединяет operations, catalogs, assessments, admins, activity.
Порядок — created_at DESC, source ASC, id DESC. from/to — включительные RFC3339;
entity_id — строка (UUID или числовой ID справочника). Системный сброс проверки компании
имеет actor_kind=system. Журнал содержит ID, действие, статусы, дату и причины новых решений;
сырые metadata старых событий, ответы, файлы, тексты тестов, пароли и токены не выдаются.

Статистика содержит согласованные счётчики пользователей, компаний, потребностей, офферов,
заданий/решений, попыток и ожидающих навыков, а также generated_at.
Открытые задания учитывают deadline. Попытки отражают сохранённый статус штатного тестирования:
административное чтение само не завершает и не оценивает просроченную активную попытку.

репозитория штатным инструментом. Последние четыре файла названы по времени создания.
Административная миграция зависит от ежедневных заданий. Сначала миграции, затем новый API:

```sh
make migrate
```

Команда использует существующий apps/api/.env. Проверить состояние:

```sh
cd apps/api
set -a
. ./.env
set +a
go run ./cmd/migrate status
```

Изменения схемы добавляют таблицы/поля и сохраняют прежние пути API. Модерация и блокировки
намеренно ограничивают доступ через прежние сценарии. Отсутствие новых таблиц не совместимо
с запуском новых модулей; последовательность миграций обязательна.

Откат истории удаляет историю и дату создания, но сохраняет офферы. Откат заданий удаляет
задания/решения/оценки, сохраняя объекты и метаданные files. Откат admin_operations удаляет
версии и данные заявок, новый аудит и поля модерации; pending становится unverified,
verified/rejected сохраняются, закрытые задания и архивные потребности остаются такими.
Перед откатом с данными нужна резервная копия; новый API не должен работать на откатанной схеме.

## 10. Проверка реализации

На 9 октября 2026 года прошли модульные тесты всего API с -race, go vet и полный прогон
**117 интеграционных тестов верхнего уровня** на изолированных PostgreSQL 17 и временном MinIO,
включая настоящую загрузку/скачивание через S3 API. После уточнений DTO повторно прошли
четыре новых сценария админки. Тестовые контейнеры удалены; рабочее хранилище не менялось.
Копии OpenAPI совпадают, ссылки спецификации разрешаются, operationId уникальны.

Покрыты изоляция компаний, права участников, приватность, фильтры и total, перенос старых офферов,
граница 30 дней, приоритет сходства перед давностью, квота московского дня, параллельная отправка,
валидация файлов, ошибки S3/БД и очистка, оценки решений, отзывы согласий,
жизненный цикл проверки компании, конкурирующие решения и сброс при изменении реквизитов,
блокировки, модерация без обхода, статистика, аудит и применение/откат/повторное применение миграций.

Проверки только бэкенда из корня репозитория:

```sh
sh scripts/check-openapi.sh
go -C apps/api vet ./...
go -C apps/api test -race ./...
```

Полный интеграционный прогон требует отдельной тестовой БД и S3-конфигурации.
TEST_DATABASE_URL и TEST_S3_* задаются в окружении; секреты в репозиторий не добавляются:

```sh
go -C apps/api test -race -tags=integration ./tests/integration -count=1
```

Тесты создают изолированные схемы PostgreSQL. Интеграционные проверки не следует направлять
на рабочее файловое хранилище. Общий make check также проверяет фронтенд; для этой работы
используются приведённые команды бэкенда.
