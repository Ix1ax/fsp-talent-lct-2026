# Кабинет работодателя: дальнейшая разработка

Текущая реализация — R1: компании, список потребностей, бриф, черновики, архив и подборка по условиям. Next.js App Router, React, TypeScript, Tailwind 4, shadcn/Radix, React Hook Form. Цвета берутся из семантических токенов `src/app/globals.css`.

## Переиспользование и границы

- `shared/ui`: Button, Input, Label, Badge, Tabs, Dialog, Sheet, Command; AccountAvatar, MetaLabel, BriefToken, SalaryRangeInput, AsyncState. Нейтральные визуальные элементы без предметных текстов.
- `entities/catalog`: SpecializationBadge, справочники и клиентский публичный entry point `client.ts`. Основной barrel также экспортирует серверные функции: браузерные runtime-импорты — из `client.ts`.
- `entities/employer-need`: модели, HTTP, названия статусов, проверка недостающих обязательных полей. Статусы и другие предметные метки остаются в entity, а не в shared.
- `features/employer-need`: модель формы, бриф, чеклист готовности, действия и меню. NeedEditor принимает footer как композиционный слот. Сохранение делает один POST/PATCH, PATCH включает только изменённые редактируемые поля; вложенные навыки проходят белый список. Транзакция на стороне backend.
- `features/company`: форма и действия компании. `features/employer-search`: поиск и загрузка страниц потребностей.
- `widgets`: оболочка, список, подборка. `screens/employer`: связывает их, URL, выбранную компанию/потребность, защиту несохранённых изменений и API-adapter.

Один HTTP-клиент и один набор UI-примитивов. Родственные features не импортируют друг друга. ESLint проверяет границы новых модулей. Универсальная абстракция для каждой строки текста не нужна: повторные визуальные подписи вынесены, уникальные тексты остаются рядом с соответствующим сценарием.

## Поиск

Работает по названиям всех потребностей текущей компании, включая черновики и архив. Ленивая загрузка при вводе двух символов, debounce 250 мс, пагинация, AbortSignal, ошибка с повтором; клавиатура через Command. Кеш живёт в компоненте и обновляется после собственных записей/смены компании. Полных результатов при ошибке одной вкладки не показываем. Ограничение offset 10000 не обходится.

Это временное решение для небольших компаний. Перед масштабированием заменить адаптер загрузки серверным поиском: `q`, `status`, `limit/offset`, `total`. Для поиска SC-кодов нужен стабильный анонимный код и разрешённый API поиска кандидатов. UUID не преобразовывать в выдуманный SC-код.

## Что требуется дальше

1. Авторизованный интеграционный прогон с работающим API: owner/recruiter/viewer, POST/PATCH, null и 0, архив/восстановление, 401/403/404, повторные запросы и сохранение формы при ошибках. Проверить транзакционность связей навыков/форматов на backend.
2. Серверный индекс поиска; totals по статусам, агрегаты совпадений/приглашений/принятых по потребности, updatedAt и сведения автора. Счётчики страницы списка не должны равняться длине одной загруженной страницы.
3. Следующие экраны: Company, Candidates, CandidateProfile, Offers, InviteForm. Подключить реальные маршруты и разрешения, состояния приглашений и получение контактов после принятия. Сейчас незавершённые разделы отключены, компания открывается в Sheet.
4. После появления соответствующего API добавить реальные SC-коды и статусы/действия в подборку. Сейчас показаны только доступные условия, неизвестные критерии и анонимный идентификатор; квалификация не оценивается.
5. Добавить интеграционные UI-тесты стабильных сквозных сценариев с контролируемым API и визуальные эталоны обеих тем на 390/1024/1440. Текущие проверки браузера выполнены вручную через автоматизацию, не являются постоянными CI-тестами.

## Регистрация и рабочий кабинет

Рабочий `/employer` уже связан с существующей регистрацией: вход/создание аккаунта в Keycloak, подтверждение почты, OIDC callback и сохранение сессии. Если `/v1/me` возвращает `not_registered`, callback показывает выбор роли. Кнопка «Я работодатель» вызывает `POST /v1/me/register` с `role: employer` и открывает `/employer`. Серверная страница проверяет сессию и роль; пользователь другой роли направляется в свой кабинет.

У нового работодателя без компаний показывается действие «Создать компанию». Создание через API в одной транзакции сохраняет компанию и назначает создателю членство `owner`. Дополнительная регистрация специально для борды не нужна.

Перед передачей рабочего сценария проверить на запущенных Keycloak и API: новый аккаунт → письмо подтверждения → выбор роли работодателя → создание компании → создание потребности → повторный вход. Этот сквозной путь с реальным новым аккаунтом пока не проверен. Для нового адреса общего деплоя также проверить redirect URI и web origins клиента Keycloak `fsp-web`.

## Демо без передачи макетов

В ветке есть самостоятельное демо `/demo/employer`: тот же EmployerHomePage с отдельным адаптером вымышленных данных. Авторизация и API не нужны, изменения живут в памяти вкладки и сбрасываются при перезагрузке. HTML-макеты и другие материалы design-handoff не импортируются.

После `npm ci` и `npm run dev -w apps/web` открыть `http://localhost:5173/demo/employer`. Сценарии через query: `?scenario=empty`, `no-company`, `viewer`, `error`, `save-error`; по умолчанию `filled`. Можно добавить `tab=draft` или `tab=archived`. Неизвестный scenario заменяется filled.

Маршрут входит в обычную сборку и доступен на общем деплое как `https://<домен-приложения>/demo/employer`. Отдельные стенд, флаг сборки или backend для демо не нужны. Это отдельный публичный маршрут с вымышленными данными, а не отключение авторизации рабочего `/employer`. Общая ссылка появится после обычного деплоя ветки.

Дизайн-исходники остаются в ignored design-handoff и исключены из Docker context. Рабочие логотипы/шрифты и лицензия включены в приложение. Старый локальный /preview/employer — личный вход, коллегам использовать /demo/employer.
