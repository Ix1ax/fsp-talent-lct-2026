# Блокировка компаний и пользователей

Администратор и superadmin блокируют компанию, работодателя или соискателя с обязательной причиной. Блокировка применяется к API при каждом запросе, включая запросы со старым действующим JWT. Обход через отключённые кнопки или прямой вызов API не даёт доступ к действиям.

## Административные методы

- `PATCH /api/v1/admin/companies/{company_id}/status` — компания.
- `PATCH /api/v1/admin/users/{user_id}/status` — аккаунт работодателя или соискателя. Для исторической роли `users.role=admin` нужен superadmin.

Блокировка:

```json
{"status":"blocked","reason":"Нарушение правил платформы"}
```

Разблокировка:

```json
{"status":"active","reason":"Нарушения устранены"}
```

Причина: 1–2000 символов после удаления пробелов по краям, без нулевого символа. Неизвестные поля запрещены. Ответ 200 — актуальная административная карточка. В ней `status`, `blocked_reason`, `blocked_at`. У активной записи два последних поля `null`. Повтор текущего статуса не переписывает дату или причину и не добавляет аудит. Для изменения причины действующей блокировки отдельного метода сейчас нет.

Запись состояния и аудит атомарны. События: `company.status_changed` / `user.status_changed`, со старым и новым статусами, причиной, ID администратора и датой. Причины прежних блокировок и разблокировок остаются в журнале.

Список компаний поддерживает отдельный фильтр `access_status=all/active/blocked`; прежний `status` фильтрует подтверждение (`pending`, `verified` и т. д.). Например:

```text
GET /api/v1/admin/companies?access_status=blocked&status=verified
```

В `GET /api/v1/admin/stats` у `companies` добавлены счётчики `active` и `blocked`. Они независимы от подтверждения.

## Действие блокировки

| Заблокировано | Ограничения |
| --- | --- |
| Аккаунт соискателя | Закрыты профиль, контакты, навыки, резюме, согласия, ФСП, тестирование, предложения и решения. Кандидат исключён из поиска и выдачи контактов работодателю; отправка ему новых предложений запрещена. |
| Аккаунт работодателя | Закрыты все защищённые действия этого аккаунта, включая создание компании, принятие приглашения и работу в любой компании. |
| Компания | Всем активным участникам (owner/recruiter/viewer) закрыты профильные изменения, команда, приглашения, документы и файлы, потребности, поиск и просмотр кандидатов, офферы/контакты, задания/решения/оценки и запрос подтверждения. Новые участники не могут принять приглашение в неё. |

У заблокированной компании задания и их файлы недоступны кандидатам; отправить решение нельзя. Офферы компании исключены из входящего списка, чтение/просмотр/ответ по ID запрещены. Новое согласие на ATS-передачу в эту компанию не выдаётся. Кандидат сохраняет чтение собственных ранее отправленных решений и их файлов: это история его работы, не новое взаимодействие с компанией. Администратор продолжает видеть компанию, документы и историю для расследования.

Аккаунт и компания блокируются независимо. Бан владельца не блокирует автоматически остальных участников его компании; для остановки всей организации используется бан компании. Бан одной компании не блокирует личные аккаунты её сотрудников и работу в другой активной компании. Разблокировка компании не разблокирует пользователя и не отменяет отдельную модерацию контента. Название, ИНН, документы, членство, согласия, результаты и статусы подтверждения не удаляются и не переписываются.

## Данные для плашки на фронте

`GET /api/v1/me` доступен заблокированному аккаунту с валидным JWT и возвращает 200. Это единственное разрешённое защищённое чтение для заблокированного пользователя: собственный статус и причина. Полные профили и рабочие API остаются закрыты. Для удалённого аккаунта сохраняется 403 `user_inactive`.

```json
{
  "id":"…",
  "sub":"…",
  "email":"…",
  "email_verified":true,
  "role":"candidate",
  "status":"blocked",
  "blocked_reason":"Нарушение правил платформы",
  "blocked_at":"2026-10-10T00:01:00Z",
  "blocked_companies":[]
}
```

Для активного работодателя `blocked_companies` содержит ID, название, `blocked_reason` и `blocked_at` каждой заблокированной компании, где он активный участник. `GET /api/v1/companies` и `GET /api/v1/companies/{company_id}` сохраняют чтение собственных карточек с теми же полями `status`, `blocked_reason`, `blocked_at`. Посторонний не получает статус или причину чужой компании. Ответы состояния не кешируются (`private, no-store`).

На фронте после `/me`:

1. Если `status=blocked`, показать плашку «Аккаунт заблокирован. Причина: …», не открывать рабочие разделы и не запрашивать полный профиль.
2. Если выбранная компания имеет `status=blocked`, показать «Компания заблокирована. Причина: …», отключить её рабочие разделы.
3. При 403 от уже открытой страницы обновить состояние и показать ту же плашку. API остаётся источником проверки доступа.

Ошибки рабочих запросов имеют прежний `error.code=user_inactive` для аккаунта и новый `company_blocked` для компании. При блокировке дополнительно возвращаются `entity_type`, `entity_id`, `reason`, `blocked_at`; для аккаунта ещё `status=blocked`. Для недоступного задания/оффера со стороны кандидата возвращается 404, без раскрытия причины блокировки чужой компании.

JWT Keycloak не отзывается. После разблокировки ещё действующий JWT снова работает. Публичные страницы, справочники и документация доступны без аккаунта: бан прекращает защищённые действия, а не анонимный просмотр сайта.

## Миграция и проверка

Новая миграция: `20261010000100_account_company_blocks.sql`. Она добавляет статус компании и текущие метаданные блокировок, переносит причины существующих блокировок пользователей из последнего соответствующего события аудита; при отсутствии события сохраняет понятную системную причину. Статус существующих компаний — `active`.

Для запуска нового backend сначала применить миграции (`make migrate`), затем перезапустить API с новым кодом. Старый запущенный контейнер не подхватывает изменения Go и встроенного OpenAPI автоматически.

Интеграционные тесты используют отдельные временные схемы PostgreSQL и синтетические объекты, не блокируют рабочие компании или пользователей. Проверяются: все рабочие маршруты для каждого типа участника, причина в профиле, действующие JWT, независимые блокировки, запрет принятия приглашения, исключение заданий/офферов, отмена загрузки решения при бане, ожидание транзакционной блокировки и идемпотентный аудит.
