# Разработка и проверка

## Перед изменениями

Прочитайте [AGENTS.md](../AGENTS.md). Сохраняйте FSD-границы и существующие
UI-компоненты. Крупные экраны разделяйте по ответственности; типы props оформляйте
как `interface`, доменные данные — как `type`. Формы используют React Hook Form
и Zod. Экспортируйте публичные функции через barrels.

Не изменяйте глобальные токены ради одного экрана. После изменения общего
компонента проверяйте его использование в других ролях и темах.
DOM ID и повторяющиеся словари выносите в подходящие константы.

## Проверки перед PR

Из `apps/web`:

```sh
npm test
npm run typecheck
npm run lint
npm run build
```

Vitest работает в Node и запускает `src/**/*.test.ts`; тесты располагаются рядом
с кодом, обычно в `__tests__`. Проверяйте ошибки контрактов, парсинг, состояние
запросов и пользовательские регрессии. SSR-тест не заменяет проверку гидратации
и взаимодействий в браузере.

Для UI проверяйте мобильную и десктопную ширины, обе темы, Tab/Enter/Escape,
состояния загрузки, ошибки, пустые списки и несохранённый ввод.
Скриншоты прикладывайте к PR с визуальными изменениями.

## Локальные сценарии API

В `scripts/review` есть mock API и браузерные сценарии. `npm run review:api`
запускает тестовый сервер, `npm run review:mock-test` проверяет его реализацию.
Для `review:baseline` и `review:auth` нужны запущенное приложение, mock API
и Chrome с доступным CDP. Эти сценарии работают с loopback-адресами.
Параметры задаются через `REVIEW_APP_URL`, `REVIEW_API_URL` и `REVIEW_CDP_URL`;
подготовка сценариев описана также в файлах `docs/review`.

## Сборка и окружение

Dev-сборка использует `.next-dev`, production — `.next`. При необходимости
изолируйте дополнительный dev-сервер через `FSP_DEV_DIST_DIR`.
Файлы `*.local.tsx` доступны только в development; их нельзя считать частью
production-маршрутизации.

Next.js собирается с `output: 'standalone'`. [Dockerfile](../Dockerfile) копирует
standalone-сервер, static-файлы и `public`, запускает приложение на порту 3000.
Сборка зависит от monorepo root для трассировки файлов. Общий деплой описан
в [README монорепозитория](../../../README.md).

## Диагностика

| Симптом                                  | Что проверить                                                                        |
| ---------------------------------------- | ------------------------------------------------------------------------------------ |
| API возвращает 404 или сеть недоступна   | `API_PROXY_TARGET`, доступность бэкенда, правильность пути `/api/v1`                 |
| Вход возвращается на логин               | OIDC redirect URI, client ID, token URL, cookies и доступность `/v1/me`              |
| Вместо названий справочников показаны ID | Загрузку серверных справочников и сообщение об ошибке                                |
| Hydration mismatch                       | Совпадение первого SSR/client рендера, DOM ID, структуру HTML, даты и условные ветки |
| Изменения не видны                       | Адрес и порт открытой страницы, текущую ветку, активный dev-сервер                   |

Не скрывайте hydration mismatch через `suppressHydrationWarning` в компоненте,
где действительно различается структура или ID. При изменении ID Radix trigger
проверьте связь `aria-labelledby` выпадающего содержимого.
Не повторяйте автоматически мутации после сетевой ошибки, если контракт не
гарантирует идемпотентность. Для длительных загрузок учитывайте AbortSignal,
отмену старых запросов и сохранность пользовательских данных.
